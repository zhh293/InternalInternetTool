# 评测限制与归档复核

## 归档时发现的本地进程清理问题

在提交2026-10-31评测证据时，逐文件SHA-256核验发现两轮`java-client.log`仍在变化。检查确认Windows PATH中的Java入口是启动包装程序：测试脚本终止了包装程序，实际JVM仍继续运行。共定位并结束11个使用固定基准测试参数和被测JAR的本地Java客户端，PID记录见[local-jvm-cleanup.json](../benchmarks/20261031-protocols/local-jvm-cleanup.json)。

这些客户端在目标服务结束后仍可能持续重连。它们可能占用Windows本地CPU、内存、线程，并在后续阶段向共同SSH承载的控制入口发起连接，因此**不能认为历史工具轮换阶段具有完整的进程隔离**。本次没有量化这种干扰，不能给出无干扰条件下的排名，也不能用现有延迟差异证明某款软件必然更快。

远端服务器临时服务及9090监听的清理记录仍保留；该记录不等同于Windows客户端进程已全部退出。报告此前关于“清理完成”的表述应限定到对应记录覆盖的范围。

## 对结果的影响与解读

- 正式请求的成功/失败、原始耗时、资源快照没有被回写。原始日志保留，包括清理后仍持续重连的尾部记录。
- 可确认的是“这些指定交互在当时条件下通过或失败”，不能据此宣称无干扰、极限性能或长期稳定性。即使重复出现的边界失败，也应在隔离环境重新验证后再推广为实现的普遍结论。
- 自建/frp的半关闭、自建UDP空报文、frp大UDP报文及WS关闭阶段表现是值得跟进的现象；现有独立夹具和网络参考可帮助定位，但并未排除全部共同承载层及残留客户端干扰。
- 首轮83/75/88分是主观权重下的有限场景成绩，不应继续用作产品完整能力或严格性能排名。

## 已完成的修正

1. 结束已核实的11个历史测试客户端，使日志停止继续写入。
2. `run_wan.py`、`suite.py`改为查询`java.home`后直接启动实际JVM，避免在Windows上只拿到包装程序的进程句柄。**归档脚本包含此项事后清理修正，不宣称与原执行脚本逐字相同**；测量逻辑及原始数据不因这项修正而改写。
3. 保留被测JAR及准确SHA-256、正式数据、脚本预检、配置复测、隔离探测和原执行日志。归档清单在日志固定后重新生成，并与Git暂存区逐字节核对。

重新给出严格性能比较前，应在修正后的脚本上复测，并在每次轮换前核对本地/远端进程和端口均已退出；还应隔离压测器、目标服务和客户端，减少共同SSH承载层的影响。当前归档没有把这项待完成复测说成已经完成。
